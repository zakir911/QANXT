# The database

PostgreSQL 16, accessed through EF Core 8. Forty-four tables plus EF's migration history.

## Conventions

**Names are snake_case.** C# says `TestCaseId`, Postgres says `test_case_id`. The mapping is
applied by a naming convention rather than by attributes on every property, so nothing drifts
when a property is renamed. `SnakeCaseNaming.ToSnakeCase` has its own tests because a
convention that is subtly wrong for one acronym (`URLValue`, `Sha256`) is worse than no
convention.

**Every table that belongs to a customer carries `organization_id`** and implements
`ITenantOwned`. Nothing is queried without that column being applied — see below.

**Identifiers are `uuid`, generated by the application**, not by the database. A worker needs
to know the id of a thing it is creating before it finishes creating it.

**Timestamps are `timestamptz`.** A test run's duration must not change because a server
moved timezone.

## Tenant isolation

This is the guarantee the schema exists to enforce, so it is worth being precise about how.

Reads are filtered by a global query filter on every `ITenantOwned` entity, applied by the
`DbContext` itself:

```csharp
builder.Entity<T>().HasQueryFilter(e =>
    IsSystemContext || CurrentTenantId == null || e.OrganizationId == CurrentTenantId);
```

A query written with no organization predicate still sees only the current tenant's rows.
There is no filter for a caller to forget.

Writes are guarded separately. On save, an entity being added gets its `organization_id`
stamped from the tenant context, and one being modified is checked against it — a write that
would place a row in a different tenant throws rather than succeeding quietly.

A few operations legitimately cross tenants: registering an organization, the agent runner
claiming queued work, a background service reconciling state at startup. Those enter an
explicit system context, with a reason that is logged, and the filter stands down for that
scope only. Searching the codebase for `EnterSystemContext` shows every place it happens.

`TenantIsolationTests` asserts both halves directly, and `AuthorizationTests` asserts them
over real HTTP: one organization cannot list, fetch or write into another's data, and gets
`404` rather than `403` because confirming that an id exists is itself a leak.

### The shapes worth knowing

**`applications` → `application_pages` → `application_elements`** is the knowledge graph,
with `page_transitions` as its edges. A page's identity is its *normalized* URL — query
values and numeric path segments replaced by placeholders — so `/accounts/1` and
`/accounts/2` collapse to one node and re-running discovery updates a page rather than
duplicating it.

**`test_runs` → `test_executions` → `test_actions`** is one run, the tests in it, and every
step of each. `test_actions` is where a step's locator, its masked value, its timing and its
healing outcome live, which is what makes an execution reviewable months later.

**`failures` → `failure_analyses` → `defects`** is the diagnosis chain. A failure is what
happened; an analysis is what the platform thinks it means, with its confidence and whether
a model contributed; a defect is a human decision. Nothing creates a defect automatically.

**`agent_runs` → `agent_steps` / `agent_findings`.** Every phase of an unattended pass with
its reasoning, and every proposal it made. An agent's conclusions are worth nothing if the
steps that produced them cannot be read back.

## Secrets in the schema

Credentials are stored encrypted, never hashed and never in plain text — the platform has to
be able to use them, so a one-way hash would not do. The envelope is
`v1:base64(nonce|tag|ciphertext)` from AES-256-GCM, and the version prefix is there so keys
and algorithms can rotate without guessing what a row contains.

Passwords for *platform* accounts are different: those are PBKDF2-HMAC-SHA256 hashes in a
self-describing `v1.iterations.salt.hash` format, because nothing ever needs to read them
back.

`SecretAndTargetTests` asserts both that a stored credential never comes back out of the API
and that the row itself does not contain the plaintext — those are different claims, and
only the second survives a database being copied somewhere else.

## Migrations

```bash
make migrate       # apply pending migrations
make db-reset      # drop, recreate, re-migrate (local only, and it asks first)
```

The API also migrates on startup, controlled by `Database:AutoMigrate`. That is right for
development and for a single-instance deployment; for several instances, turn it off and
migrate as a deploy step, or two instances will race.

To add a migration:

```bash
dotnet ef migrations add <Name> \
  --project apps/api/src/QaNxt.Infrastructure \
  --startup-project apps/api/src/QaNxt.Api
```

Migrations live in `apps/api/src/QaNxt.Infrastructure/Persistence/Migrations`.

## Transactions

`InTransactionAsync` wraps work that must be atomic. It runs inside EF's execution strategy,
because connection resiliency retries a failed command and would otherwise replay only part
of a manual transaction — a retry has to restart the whole thing. The in-memory provider used
by some unit tests has no transactions, so it runs the operation directly there rather than
pretending.

## Testing against it

The integration suite creates a database per run and drops it afterwards. It deliberately
does not substitute an in-memory provider: the query filters, the snake-case mapping and the
migrations themselves only exist when the real provider is there, and a suite that passes
against a fake database and fails against Postgres is worse than no suite, because it is
trusted.
