## Problem Statement

A QA lead at a bank signs off each release of a web application on the strength of manual testers working through written test cases. Coverage is whatever the team had time for, evidence is scattered, and the lead's name goes on the release anyway. QA NXT can already design and run every form-, field- and page-level test deterministically. But on the first real locked-down application (HFCB Retail Banking), it could not reliably get in, so it could not reach the forms. The first full run then generated 122 tests for 19 pages, and 108 of them never ran. The problem to solve is not "generate more tests". It is getting a locked-down application to a release sign-off a QA lead will put their name to.

## Demand Evidence

- The founder's own pain: they test applications like HFCB by hand today (Q1). No outside user or payment yet: one data point, not a market.
- The founder's sharpest stated requirement, on an earlier report: "I dont want the application to flag issues which are not exactly bugs." Trust in verdicts is the demand signal that exists.
- Stated goal: "create all possible test cases for each and every forms, pages & fields" and "replacing a QA completely".

## Status Quo

Manual testers execute written test cases (Excel, Jira or TestRail) each release (Q2). The cost is testers multiplied by days per release; the founder gave no numbers yet. Coverage depends on time available and evidence is whatever testers attach.

## Target User & Narrowest Wedge

- **User:** a QA lead or test manager who owns the test plan and release sign-off (Q3). Promoted for releases that ship on time without escapes; fired for a missed critical defect.
- **Wedge:** one locked-down web application in a non-production environment. QA NXT gets in through a guided sign-in, tests every signed-in form and field, and hands the lead a sign-off pack for one release. Narrowest test of willingness to pay: would the lead sign a release on that pack instead of a manual cycle?

## Constraints

- Regulated customers (banks): applications and data may not be sent to an AI model; the product must work with AI disabled and run inside the customer's network.
- Test environments are locked down: OTP, sessions held only in the page, one session per user, slow or partially blocked pages (all seen on HFCB).
- Production must not receive test submissions by default. The only exception is an audited opt-in per environment: an organisation admin enables it, it names the person and the date, and every run and sign-off pack using it shows it.
- Pre-product: one founder, one real trial application, no paying user.

## Premises

1. The promise is "one QA lead gets the coverage of a ten-person team, with sign-off evidence", not "replace a QA". (Agreed.)
2. Day one is a guided setup: the QA lead records the sign-in once (typing the OTP themselves) and QA NXT keeps and reuses the session. Automatic sign-in is the fallback for unattended runs. Until a new application reaches its signed-in forms, test count is irrelevant. (Revised after the second opinion; original said "unaided".)
3. Trust beats volume: the measure is approved tests that ran, with evidence and no false failures, across the application's real flows. (Agreed.)
4. A deterministic engine that works with AI off and runs inside the customer's network stays the differentiator. (Agreed.)

## Cross-Model Perspective

Independent cold read by a fresh Claude subagent; Codex is not installed, so this is the same model family.

- **Steelman:** "a QA lead's sign-off engine for regulated web apps: point it at a locked-down app and, inside the bank's network with no AI, it gets in and stays in, tests every form and field with evidence, and hands back a release pack that survives an audit."
- **Most revealing answer:** "I dont want the application to flag issues which are not exactly bugs." One false failure costs more trust than 1,000 extra generated tests earn. Build the result-trust layer (separate "failed" from "couldn't run", review gate) before more volume.

## Approaches Considered

### Approach A: HFCB day-one proof (minimal viable)
Guided sign-in (record once, a person types the OTP, the session is saved), then signed-in discovery and runs on HFCB. Effort M (human ~1 week / CC ~2-3 h), risk low. Gives the buyer nothing to sign; it is the first slice of B.

### Approach B: QA lead's sign-off engine (chosen)
A, plus session health, production guard, review gate, three-state verdicts, a sign-off pack and trust metrics. Effort L (human ~4-6 weeks / CC ~1-2 days), risk medium.

### Approach C: their test plan, automated (lateral)
Import the lead's existing Excel or TestRail cases, map them to discovered forms, automate what can be, and report coverage of their plan. Ruled out for now: matching free-text cases to fields is fuzzy and still needs A to get in. Worth revisiting as a sales motion once B exists.

## Recommended Approach

**B, built in this order** (each step usable on its own):

1. **Guided sign-in (A's slice).** A person supplies only what a machine cannot: the OTP. What the run does with the session depends on where the application keeps it. The worker already measures this after every sign-in, by checking whether a second tab is still signed in (`checkSessionSurvivesLoad`).
   - **The session survives a page load** (a cookie or local storage): after the guided sign-in, the session is saved as the application's storage state and reused by later jobs.
   - **The session lives only in the page** (HFCB): nothing can be saved. The run signs in once, pauses at the OTP screen, and asks the lead for the code on the run's page in the console (an "Enter the code sent to you" prompt, with a timeout). It then runs all its tests in that one signed-in browser, one after another, and signs out at the end. One run is one session.
   - **Where the browser runs:** the worker, headless, as today. The lead never needs a browser on their machine; the code travels from the console to the paused run. Whether a full recorded login through the extension is also offered is an engineering-review decision; it is not needed for HFCB.
   - **One session per user:** jobs that share a test account never run at the same time (the session gate already enforces this per application and account). The health check reuses the run's own session and never signs in on its own. If the application ends the session because someone signed in elsewhere, the affected and remaining tests are marked not run with "session lost", never failed. The lead is shown this on the run page, along with a "sign in again" action.
   - **Between tests in one shared session:** nothing is reloaded. The worker presses Escape to close any open dialog, then moves inside the application back to the signed-in landing page recorded at sign-in. It checks that page is showing: its address, and no sign-in form. If the check fails, the remaining tests are not run with "could not return to a clean signed-in page", never failed. Tests that need data a previous test changed are out of scope here; data clean-up is a separate gap (#4 in the completeness review).
   - **Mid-run loss:** before each test, and again whenever a step lands on the sign-in page or its address, the worker checks the run is still signed in. Losing the session ends the run's remaining tests as not run with "session lost".
   - **Credentials and identity:** QA NXT requires a dedicated test account per application. The console states that every action runs under that account in the bank's audit logs. A saved session is encrypted like other credentials, usable only by that application's jobs in the same environment, and deleted when it expires, is re-recorded, or the application is deleted. In-page sessions are never stored.
   - Automatic sign-in with a fixed test code or an authenticator secret (already built) remains for unattended runs, where the bank provides such a code.
2. **Production guard.** It fails closed. Every environment must be classified as production or non-production before tests run against it. An unclassified environment is treated as production. On production:
   - sign-in, sign-out and read-only discovery are allowed. Requests made while the sign-in or sign-out step is running are exempt, and only those; the worker knows when it is inside those steps;
   - outside sign-in and sign-out, the worker blocks every non-GET request the browser would send (intercepted at the network layer, so a button that sends a fetch is caught like a form submit), including POSTs the application uses for read-only searches, and every changing API step;
   - a test that needs one is marked not run, with "production: submissions blocked".

   The only exception is the audited opt-in described under Constraints. This closes gap #1 in docs/QA-COMPLETENESS-REVIEW.md.
3. **Review gate.** Generated tests start as Proposed, and the lead approves them in bulk, by form and testing type, before they run.
   - New tests from a later generation start as Proposed.
   - A test the generator changes because its form or field changed returns to Proposed, showing what changed.
   - Unchanged approved tests stay approved; rejected tests stay rejected.
   - Tests a person edited stay as edited and are flagged for review (the generator already preserves edits).
4. **Three-state verdicts everywhere.** Each test ends as passed with evidence, failed with evidence, or not run with its reason. "Not run" never counts as passed or failed.
   - **Failed** only means the application was reached and behaved differently from what the test expected, with evidence: a check that compared what was expected with what was observed.
   - **Not run** means one of the following, with the reason recorded:
     - sign-in or session loss;
     - the production guard;
     - a page that did not load or answer;
     - a timeout before the page was ready;
     - a blocked resource;
     - a locator for an element the test needed that was not found on a page that otherwise loaded and was signed in. This is reported as "could not find X". Healing may propose a fix, and a person decides.

   The existing Blocked, Skipped and Error statuses all map to not run. The existing Failed and TimedOut statuses map to failed only when an assertion produced the mismatch.
5. **Sign-off pack.** One HTML/PDF per release (a run, or a set of runs against one build). It shows coverage per form and field, verdict counts, defects by severity, the security scan, outstanding human checks, and evidence links. It builds on the existing bug-report renderer and coverage service.
   - **Build:** identified by the build reference the lead enters when starting the run. A run already carries an optional ApplicationBuildRef, and the CLI and CI set it. A run without one cannot be signed off.
   - **Signing:** allowed with failed or not-run tests. Their counts and reasons are on the pack's first page, and the signer must tick that they have seen them. Signing records who, when and the build.
   - **After signing:** the pack is frozen, stored with a content hash and never regenerated. Re-signing after more runs creates a new version.
6. **Trust metrics on the dashboard:** the percentage of approved tests that ran, and the false-failure rate (defects the lead rejected as not bugs).

## Open Questions

- Which sign-off format does HFCB's (or a bank's) release process require: an internal template, or an auditor's checklist? It decides the pack's sections.
- How long does an HFCB session last idle, and does a recorded session survive long enough for a full run (15 minutes, 8 hours)? It decides how often a person must re-record.
- Should approval be per test, per form or per testing type by default? The wireframe assumes per form, with a drill-down.
- Can the worker run inside the bank's network (on a tester's machine or a jump host)? This environment cannot reach hfcdevs.com at all.

## Success Criteria

- A new locked-down application reaches its signed-in forms within 30 minutes of the QA lead starting setup, with no code change.
- On HFCB non-prod: at least 80% of approved tests actually run, and none of their failures is rejected by the lead as not a bug (zero false failures).
- One QA lead other than the founder says, in their own words, that they would sign a release on the pack, or names exactly what is missing.
- The full form-lab verification stays at 0 failed, with no false failures.

## Distribution Plan

Unchanged: the existing self-hosted deployment (make dev / containers). The guided sign-in needs no browser on the lead's machine. The worker runs headless as today, and the OTP is relayed from the console to the paused run. Whether to also offer a full recorded login through the existing browser extension is the only open engineering-review decision here.

## Dependencies

- Existing: StorageState authentication strategy, browser recorder extension, sessionGate and in-app navigation, bug report renderer, coverage service, defect confirm/reject, environments with an IsProduction flag.
- Network access from wherever the worker runs to the customer's test environment.

### R2-1 — consistency (blocking)

**Problem**

> On production the guard allows sign-in and read-only discovery, but also blocks every non-GET request at the network layer. Sign-in (credentials and OTP submission), and often sign-out, are POST requests, and many applications use POST for read-only queries (search, GraphQL). As written, the guard either blocks the sign-in it permits or needs an unstated exemption, which would itself be a hole in a fail-closed guard.

**Remedy**

> Specify how sign-in (and sign-out) requests are exempted on production, for example an allow-list limited to the recorded sign-in step's endpoints, and state that all other non-GET requests, including read-only POSTs, stay blocked, with the affected discovery or tests marked not run.

### R2-2 — feasibility (blocking)

**Problem**

> For in-page sessions every test shares one browser and one session, and a page load signs the user out. The design does not say how the browser is reset between tests without a reload (half-filled forms, open modals, changed data, a different page). Leftover state from one test can make the next fail, producing the false failures the success criteria forbid.

**Remedy**

> Define the reset between tests in a shared in-page session: in-app navigation back to a known signed-in landing page, without a reload, with a check that the expected page is shown. Say that a test whose starting state cannot be reached is not run with a reason, never failed.
